# Runbook

Production: https://sodhsetu.in (the CI health check and the watchdog use it; https://scholar.shodhsetu.workers.dev still answers while people move over, `www` redirects to the bare name; Worker `scholar`, D1 `scholar-db`, R2 `scholar-files`, queue `scholar-jobs`).

## Deploy

Every push to `main` runs CI, and only if it passes, deploys:

1. typecheck, unit tests, citation eval (replay), web build, **integration** (real Worker + local D1 + fake IdP), `npm audit`
2. apply D1 migrations to production
3. `wrangler deploy`
4. check `GET /api/v1/health` (fails the run if the service is down or the database is not migrated)

Manual deploy (only if CI is unavailable): `npx wrangler login`, then `npm run deploy`.

## Check that production is healthy

Two addresses, both answer 200 when well and **503** when not, and neither shows anything private:

- `GET /api/v1/health`: `{ok, db, migrations, version}`. 503 if D1 is unreachable or no migrations are applied. Used by the deploy check.
- `GET /api/v1/health/jobs`: whether the daily job ran on time. 503 if it failed, did not finish, or has not run for 30 hours (see "Alerts"). Staging answers `{"scheduled": false}` because it has no schedule.

An hourly check of both is already set up (the Watchdog workflow, see "Alerts"). For minute-level alerts point an uptime service (for example UptimeRobot, free) at the same two addresses and alert on non-200.

## Roll back

Code: `npx wrangler rollback` (pick the previous version), or revert the commit and push. Migrations are forward-only, so
**every migration must keep the previous version of the code working** (add columns/tables first, remove old ones in a later
release). That is what makes a code rollback safe.

Data: see "Backups and restore" below. In short: `npx wrangler d1 time-travel restore scholar-db --timestamp=<time before the damage>`, then the checks on `/admin`.

## Logs

Workers Logs are on (Cloudflare dashboard → Workers → scholar → Logs). Each request writes one JSON line:
`{level, msg:"request", requestId, method, path, status, ms, cfRay}`. Query strings are never logged. A user can quote the
`X-Request-Id` response header or the `requestId` in a 500 body; search for it.

After rotating a pasted-in-chat credential, revoke the old one at the provider.

## Limits and housekeeping

- Rate limits: `ratelimits` in `apps/api/wrangler.jsonc` (search 60/min, other API 240/min, per IP). Change and deploy.
- Cron (daily 03:17 UTC) deletes expired cache, sessions and OAuth states and old usage rows. Every run leaves a heartbeat in the `job_runs` table (started, finished, ok or failed, last error), shown on `/admin`
  under "Scheduled jobs" and reported by `/api/v1/health/jobs`, so a trigger that stops, a run that throws and a run that hangs are all noticed. The log line `{"msg":"maintenance","deleted":{...}}` is still written.
  `EXPECT_CRON` ("1" in production, "0" in staging) tells the health address that the job is expected; the migration counts as the first good run.
- The same cron runs a second job, `retraction_check` ("Retraction re-check of saved papers", S3, [design/s3-retraction.md](design/s3-retraction.md)): every saved paper's DOI is asked about at Crossref at most once a week (400 a run, in groups of 40, through the shared Crossref lane), what is learned goes to `paper_retraction` (shared, no person) and a notice to `library_alerts` for each person who saved a paper that turned out to be retracted. Its heartbeat is listed beside the clean-up (same alerting). The log line `{"msg":"retraction_check","result":{"checked":..,"retracted":..,"unknown":..,"alerts":..}}` says what a run did. If it fails (Crossref down), the earlier groups of that run are kept and the next night continues; there is no Run button for a deployed Cron Trigger that Cloudflare documents (its Cron Triggers page describes manual testing for local development only; the dashboard adds, lists and deletes triggers and shows the last 100 events), so to run it by hand add a one-off trigger as "Start it sooner than the nightly cron" under "The Trending list" says (every trigger runs all three jobs). To see what is known: `SELECT state, COUNT(*) FROM paper_retraction GROUP BY state`.
- The same cron runs a third job, `trending` (the Home page's Trending list: see "The Trending list" below). It has its own heartbeat beside the other two, seeded by migration 0025, so `/api/v1/health/jobs` lists three jobs and answers 503 if the Trending job failed, hung or did not run for 30 hours. It keeps its list in KV, not in the database. A failed run leaves the last good list in place.
- The nightly purges run in pieces of 5,000 rows, with a 25-second budget ([design/scalability.md](design/scalability.md)). One failing purge does not stop the others, but the run then fails and names it
  on `/admin` and `/api/v1/health/jobs`. A `maintenance_budget` warning in the logs means the run stopped early and the next night continues; several nights in a row means a table grows faster than it is emptied.
- Migration 0024 adds `library_items.doi` (a copy of the paper's DOI, kept by the code on every save). If a paper is ever written to `library_items` by hand, set the column too, or its retraction check is skipped.
- Scanned papers: pages per person per day is the Worker variable `OCR_PAGES_PER_DAY` (default 60; a value that is not a whole number from 1 to 2000 is ignored). It is a plain
  variable, not a secret: set it in `wrangler.jsonc` `vars` (and the staging block) and deploy. Cost and how it works: [ocr.md](ocr.md).
- Semantic Scholar: calls go through the `S2Throttle` Durable Object (1 request/second); Crossref and CORE through `ApiGate` (next section). S2 also returns 429 on its own
  under load; the search then reports `s2` as failed and still returns the other three sources. That is upstream, not a bug.

## Uploaded papers

PDFs and covers live in R2 (`scholar-files`, keys `docs/<user>/<id>.pdf`), text and vectors in D1 (`doc_chunks`), answers in `doc_qa`.
Limits are in `packages/shared/src/documents.ts`. An upload that stops half way leaves a paper in "uploaded" or "indexing":
the user sees **Index again** on its card, which re-reads the stored PDF in the browser and re-sends the text; nothing to do server side.
Orphaned R2 objects can only appear if a delete fails between the file and the rows, or after a database restore. `/admin`, "Data checks", **Compare papers with stored files** lists both kinds
of drift (a paper without its file, a file without a paper) by short paper id; files and papers younger than 15 minutes are not judged. It is read only. `QA_STUB` must never exist in production (the secrets script refuses to upload it).
A question uses one gateway call (about 3 to 4k tokens); the per-user daily token quota is in `src/llm/config.ts`.

## Idea Check, reports and the admin page

- **Idea Check** (`/idea`): the idea text is sent to `POST /api/v1/idea/plan` (private model), is not stored and is not logged. Only the approved search plan
  goes to OpenAlex and Semantic Scholar. Nothing about a check is kept server side.
- **Comparison and second reading** (`POST /api/v1/idea/compare` and `/idea/insights`): the researcher asks for each; each is one model call on the private route, streamed as stages, nothing stored. Measured with the real model
  (22 Oct): about 5,500 tokens and 20 to 60 s for the comparison, about 6,500 tokens and 25 to 80 s for the second reading (its time limit is 150 s); a whole check is 12,000 to 14,000 tokens (23 Oct: the earlier 19,000 to 24,000 counted streamed
  output twice, see [spikes/R5-cost.md](spikes/R5-cost.md)), so the 60,000 a day is about five checks (roadmap D6). Locally, with `ENABLE_DEV_ROUTES=1` and a real model, the Worker logs every claim it dropped (`compare_dropped`, `insights_dropped`, with the quote and the abstract) so the prompts can be tuned; never in production.
  `node apps/api/scripts/idea-live.mjs` runs all of it on three real ideas (use `LIVE_SUB=<name>` for a fresh test user when a day's allowance is used up).
- **OpenAlex budget.** The API key has a daily budget of **$1** (response header `X-RateLimit-Limit-USD`), about 1,000 searches, shared by production, local testing and the
  eval. When it is used up OpenAlex answers 429 until the reset (`Retry-After` seconds): search then reports `openalex` as failed and the other sources carry on, Idea Check
  reports the failed searches, and the Verifier falls back to Crossref. A full `npm run eval:record` uses a large part of the day's budget: do not record while testing live.
  Check what is left: `curl -sI "https://api.openalex.org/works?per-page=1&select=id&api_key=KEY" | grep -i ratelimit`.
  A separate key for development and the eval, or prepaid credit, removes the problem.
- **Reports** ("Report a problem" on an answer, a reference or an idea search) go to the `feedback` table and are kept for a year (cron) or until the account is deleted. They are
  listed on `/admin`. Make someone an admin in D1: `npx wrangler d1 execute scholar-db --remote --command "UPDATE users SET role='admin' WHERE email='you@example.com'"`
  (sign out and in again). The admin overview shows counts, AI use per day and per model, failures and reports; it never shows paper or idea text, and shows people only as a short id.
- **Someone asks to delete their data and cannot sign in:** `/admin`, **Erase an account**. Type their e-mail address or ORCID iD, press Erase, confirm. It is the same erasure as "Delete my account"
  (papers, files, library, reports, sign-in, and the deletion marker that keeps a restore from bringing the account back). It signs the person out, refuses your own account and any other admin (remove the role first with
  `UPDATE users SET role='scholar' WHERE email=...`), and the address typed is used for one lookup and not stored. The audit log records "account_erased_by_admin" without saying who.
- Answers reported as wrong are the raw material for the Q&A gold set: copy the question and passage into `apps/api/scripts/r2/questions.json` (new `id`) once the right answer is known.
- **Weekly Q&A quality** (`.github/workflows/qa-eval.yml`, Tuesdays): downloads the five public gold-set papers, asks the 35 questions with the real models and fails below the gate
  (`qa-eval.mjs --gate`). It needs the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets. First run: trigger it by hand (Actions, "Q&A quality", Run workflow).

## Streams: the event rule, and how answers went (27 Oct 2026)

Design: [design/research-patterns.md](design/research-patterns.md), sections 1 and 3.

- **The rule for every stream the server sends: progress and text are different event types.** A *progress* event (`step`, `stage`, `ingest`) says that work is moving and never carries the words of an answer; a *text* event (`token`, `general_token`, `delta`) carries nothing but `text`, is provisional and is replaced by the result event that follows; a stream has exactly one *end* event and it is last (`done`/`error` for chat and Idea Check, `answer`/`error` for a question about a paper); the reading progress of a paper (`ingest.progress`) is a number from 0 to 1 that never goes back. The table of every event type and its kind is `packages/shared/src/stream-shape.ts` and is typed against the event unions: **a new event type does not compile until it is classified**. `streamShapeProblems` checks a recorded stream; the endpoint tests (chat, Idea Check, questions about a paper, Ask this paper) run it on every stream they read and report it on their last line.
- **A new stream or a new event:** add the type to the union, classify it in `stream-shape.ts`, and write the test for any rule it needs. Keep-alive stays an SSE comment line (`sse.ts`), never an event.
- **How answers went** (`answer_outcomes`, migration 0019, counts only: a day, a feature, an outcome, a number; no text, no person, no paper; kept 90 days): the admin page shows the last seven days under "How answers went". The line to watch is how often the model wrote an answer that our own check then refused (`not_grounded`) among the questions the papers could have answered. It decides whether a "check again" step is built: under about 5% it is not worth it.

## Open-access papers (W4, the shared index)

Design: [design/oa-w4.md](design/oa-w4.md). A paper is read once into `oa_papers` / `oa_chunks` by a Cloudflare Workflow (`OaIngest`, binding `OA_INGEST`, named `scholar-oa-ingest` in production and `scholar-oa-ingest-staging`). The first deploy that contains it creates the Workflow; nothing else to set up.

- **Look at it**: the admin page ("Open-access papers in the shared index") shows how many are ready, being read, failed for now, or cannot be read, and the reasons. Instances: `npx wrangler workflows instances list scholar-oa-ingest` and `... describe scholar-oa-ingest <instance>` (an instance is `oa-<hash>-<attempt>`; the row in D1 names its current instance).
- **A paper that is stuck "reading"**: it gives itself up after 15 minutes and is tried again by whoever asks next. To do it by hand: `UPDATE oa_papers SET status = 'failed', retry_after = NULL WHERE key = 'doi:...'`.
- **Read a paper again** (a bad extraction, or its source changed): delete its row, `DELETE FROM oa_papers WHERE key = 'doi:...'` (its passages go with it), and the next question reads it afresh. Its file stays in R2 under `oa/<hash>/` until overwritten.
- **A paper that cannot be read** (`unreadable`) stays so: `blocked`, `scanned`, `too_long`, `not_open_access`, `wrong_paper`. A `failed` one (download failed, timeout, our fault) is tried again after an hour.
- **Limits**: 20 new papers a person a day and 300 for the whole service (`oa_daily`, the row with user `*`). To raise the service's brake, change `OA_NEW_PAPERS_PER_DAY_ALL` in `packages/shared/src/oa.ts`.
- **After the first deploy, check** the share of papers that become `ready` against what spike R8 measured (about 55% of publisher PDF links fetchable by a server; Europe PMC XML and arXiv always), from a few real searches. If Cloudflare's addresses are blocked by publishers more than a laptop was, the ladder's third step is the one that suffers; the other two do not.
- **Cost**: a first reading is one download, text extraction (CPU seconds), and 60 to 600 embeddings: cents at most; a shared paper is paid for once.

## The shared lanes to Crossref and CORE (V5)

- Every call to **Crossref** and **CORE** first asks one Durable Object, `ApiGate` (binding `API_GATE`, one instance per lane: `crossref`, `core`), so the limit holds for the whole product and not per process.
  Settings are in `apps/api/src/gate/index.ts` (`GATES`): Crossref a start every 340 ms and three at once (what its polite pool says in `x-rate-limit-limit` and `x-concurrency-limit`); CORE nine starts a minute and 800 a day (it allows ten a minute; the daily
  allowance of 1,000 is from CORE's documentation, nothing in its answers shows it). State is kept in the object's storage, so a restart does not forget what was spent.
- A call the lane cannot place in time is **not made**: Search gives up after 2.5 s and goes on without Crossref, a reference check queues up to 15 s. To the caller it looks like a 429, which every caller reports as "could not check", never as "not found".
  When Crossref or CORE answer 429 themselves, the lane is closed for the time they ask (CORE: its `x-ratelimit-retry-after`), so the other callers do not walk into the same wall.
- If the Durable Object cannot be reached, each isolate keeps its own lane (a log line `gate_unreachable` is written once per isolate): a little too loose is better than every lookup failing.
- Look: no page yet. A burst test against a deployed Worker: `node apps/api/scripts/crossref-burst.mjs <base url> refs 40 15 <offset>` (use a new offset each time: answers are cached). Local: `scripts/gate-e2e.mjs`, part of `npm run integration`.
- Change a limit: edit `GATES` and deploy (the object reads it when it starts; to apply it at once change nothing else, a deploy restarts it). Reset a lane that was closed by mistake: deploy; or delete the object's storage key `state:<lane>` (Dashboard, Durable Objects, `ApiGate`).
- Adding a lane for another service: add it to `GATES`, wrap the call in `withGate(name, maxWaitMs, ...)`, and say in the wording of its errors that it is busy, not "HTTP 429" (Idea Check retries that after a pause).
- Numbers and why: [spikes/R7-lanes-and-core.md](spikes/R7-lanes-and-core.md).

## The public cache (Workers KV)

- Search results, DOI and retraction checks, reference lookups and public model answers are remembered in **Workers KV**, binding `CACHE` (namespace ids in `apps/api/wrangler.jsonc`: `scholar-cache`, and `scholar-cache-staging` for staging). Only public data goes in it; never a person's text, file or idea.
  Entries expire by themselves (a day to a week; "not found" six hours); nothing to clean up. Why KV, what it can and cannot do, and what was measured: [spikes/R6-kv-cache.md](spikes/R6-kv-cache.md).
- Look: `/admin`, "Public lookups kept" (hits and misses per source, 7 days). Contents: `wrangler kv key list --namespace-id <id> --remote` (use the staging id for staging).
- Throw everything away: change `KV_VERSION` in `apps/api/src/cache/kv.ts` and deploy. Go back to the database table: remove `kv_namespaces` from the config and deploy; the code uses `api_cache` by itself when `CACHE` is not bound
  (the daily job still cleans that table, and `cache_stats` older than 35 days).
- A deploy needs the namespace to exist already (it does; created with `wrangler kv namespace create`). A new environment needs its own namespace and a `kv_namespaces` entry.

## Search text, and the switches of the understanding work (4 Nov 2026)

- **A provider's text is made plain text as it is read** (`plainText` in `apps/api/src/search/normalize.ts`, applied in `runProvider`): the title, journal, authors and abstract lose HTML entities (`&amp;`), tags, tabs, line breaks and invisible characters, and keep Devanagari's joiners. It is applied **after** the cache, so the cache key and what the cache keeps are what the source sent: nothing to purge, going either way. Idea Check, the literature scan and Trending read the same cache and get the same clean text.
- **Switch it off: the Worker variable `SEARCH_PLAINTEXT` set to exactly `off`** (lowercase; `OFF` or `off ` leave the fix on). It gives back what the adapters returned for the title, journal, authors and the OpenAlex, Semantic Scholar and PubMed abstracts. It does **not** reach the adapters' own `stripJats`: Crossref's abstract and DOAJ's title and abstract are cleaned while the response is read, with the switch off too. Idea Check's meaning-search lane is not cleaned at all. As with `CHAT_CONTEXT`, a variable set by hand lasts only until the next deploy: to keep it, put it in the `vars` of `apps/api/wrangler.jsonc`.
- **Flags of the understanding work** (`apps/api/src/understand/flags.ts`; none exists yet, the reader is ready). Each new behaviour has one flag with the positions `off` (today, byte for byte), `shadow` (compute and count, change nothing on the wire) and `on`; the safety lane also has `core`. **Unset is off.** A variable that is not exactly one of the positions (`ON`, `true`, an empty string) is off and counted as a bad value, because a flag turns behaviour on and a typo must not.
- **Lowering a flag without a deploy: a KV override.** The key `flag:<NAME>` in the `CACHE` namespace holds a position, and the flag stands at the **lower** of that and the variable. An override can never raise a flag; that takes a deploy. Write it exactly `off`, `shadow` or `core` (case and spaces do not matter) and **read it back**: `wrangler kv key put "flag:<NAME>" off --namespace-id <id> --remote`, then `wrangler kv key get "flag:<NAME>" --namespace-id <id> --remote`. A key that holds anything else (`of`, `"off"` with its quotes, an empty string) is ignored and counted as a bad override, so the flag stays where the variable puts it: a typo in an incident does not lower it. It reaches a place in about a minute (KV's shortest edge cache is 30 s, and a Worker keeps what it read for 30 s). With the variable `off` there is no KV read at all.

## Error reporting (Sentry)

Unexpected errors in the Worker, a failed daily clean-up, and errors in people's browsers go to Sentry through our own small client (`apps/api/src/monitoring/`). No SDK is
installed. Only the error type, a message shortened and stripped of e-mail addresses, links and ids, the stack, and a route pattern (never a URL with ids or a query) leave; no request, user, IP, cookie or
text a person typed. The browser posts to `/api/v1/monitoring` and the Worker forwards it, so the page's Content-Security-Policy is unchanged and the Sentry key never reaches the browser.
At most 20 events a minute are sent from one Worker instance, so a failure loop cannot use up the free quota (5,000 errors a month on Sentry's free Developer plan).

Set it up (once): in Sentry create a project (platform: Cloudflare Workers or JavaScript), copy its **DSN**, then
`npx wrangler secret put SENTRY_DSN` (or put `SENTRY_DSN=...` in `apps/api/.dev.vars` and run `npm run secrets:push -w apps/api -- --only=SENTRY_DSN`). Then open `/admin` while signed in as admin and press
**Send a test event**: it should say Sentry accepted it, and a "Test event from the admin page" appears in the project. Every press is a new Sentry issue (the time is in its message), so an alert on "a new issue is created" fires each time; it is sent at error level so the alert rules are tested the way they will be used. Optional: `SENTRY_ENVIRONMENT` (default `production`).

## Backups and restore

Rehearsed on 22 Oct 2026 on staging (`node apps/api/scripts/restore-rehearsal.mjs --yes`, about 80 s): put rows in every table, took a restore point, wiped every table and dropped one, restored (4.5 s), and every table, row and the schema came back
identical; restoring to the bookmark the command printed brought the wiped state back exactly (so a restore can itself be undone); a plain SQL export loaded into a fresh database gave the same rows. Run it again before launch, after any change to the data layer,
and about every quarter. It only ever touches `scholar-db-staging` (it refuses to run if `env.staging` points anywhere else).

| What | Copy | How it comes back | Reach |
| --- | --- | --- | --- |
| D1: accounts, library, paper text and vectors, questions, notes, reports | D1 Time Travel, built in, nothing to schedule | `wrangler d1 time-travel restore` | any minute of the last **30 days** (Workers Paid; 7 days on the free plan) |
| The same, as a file | `npx wrangler d1 export scholar-db --remote --output=<file>.sql` | load it into a database with `wrangler d1 execute <db> --file=<file>.sql` | the day you took it. Take one before a risky migration. It contains personal data: keep it encrypted, off shared drives, and delete it within 30 days (the privacy text promises 30) |
| R2: the PDFs and covers | **none** (no versioning in R2) | the owner uploads the PDF again; the records stay, and "Index again" re-reads it | not restorable. A copy would outlive an account deletion, so none is kept on purpose |
| Secrets | not readable back from Cloudflare | names are in `apps/api/.dev.vars.example`; keep the values in a password manager | |
| Code | GitHub | `git` | |

**To restore the database** (after a bad migration, a wrong `DELETE`, a bug that damaged rows):

1. Stop the damage first: `npx wrangler rollback` for a bad deploy. Note the time just before it started.
2. `npx wrangler d1 time-travel info scholar-db` prints the current bookmark. Write it down: it is your undo.
3. `npx wrangler d1 time-travel restore scholar-db --timestamp=<ISO time before the damage>` (add `--json` to read the answer). It prints the bookmark it replaced; keep that too.
4. Check `/api/v1/health` (200) and a count: `npx wrangler d1 execute scholar-db --remote --command "SELECT COUNT(*) FROM users"`.
5. If the restore point is **before a migration**, the code expects a newer schema: run `npm run db:migrate:remote` again (migrations are forward only and re-apply) or roll the code back to match.
6. Open `/admin`, "Data checks", and run both, in this order:
   - **Re-apply deletions after a restore.** Someone who deleted their account after the restore point comes back with the restore. When an account is deleted a marker with its random id is written to R2 (`tombstones/<id>`; R2 is not rolled back by a D1 restore); this erases again every account that has a marker and a row. Not doing this would keep data we promised to delete. Markers expire after 35 days (R2 lifecycle rule `deletion-markers` on `scholar-files` and `scholar-files-staging`), a few days longer than the 30 days a restore can reach back.
   - **Compare papers with stored files.** Files uploaded after the restore point have no record any more (orphans: delete them in the R2 dashboard once you are sure, under `docs/<owner>/`); papers whose file was deleted after it have a record but no file (the owner can delete the card and upload again).
7. Tell people what they will notice: sign-ins and sessions after the restore point are gone (sign in again), and anything saved, uploaded, asked or reported after it is gone.
8. If it did not help, restore to the bookmark from step 2 to undo it.

What a restore does not cover: R2 files; Sentry and GitHub history; anything an outside service already received.

## Alerts

What can go wrong and what notices it. Everything below sends a GitHub issue, which GitHub e-mails to people watching the repository, except Sentry, which e-mails by its own rules.

| What goes wrong | What notices | Where it shows |
| --- | --- | --- |
| The site, its database or its web app are down, or a deploy left the database unmigrated | **Watchdog** workflow, hourly (`.github/workflows/watchdog.yml`, script `.github/scripts/watchdog.mjs`): `/api/v1/health`, `/api/v1/health/jobs`, `/`. Each is tried 3 times, 15 s apart, before it counts | issue "Workflow failed: Watchdog" with the reason (for example `service: HTTP 503 (ok=false db=error migrations=0)`) |
| The daily job did not run, threw, or hung | the `job_runs` heartbeat, read by the Watchdog (`daily job`), by `/admin` ("Scheduled jobs") and by Sentry (the exception) | same issue, and the admin page |
| A workflow failed: CI on `main` (including the deploy), Q&A quality, Eval (live APIs), Browser e2e, Watchdog | an `alert` job at the end of each (`.github/scripts/workflow-alert.mjs`) | one issue per workflow, "Workflow failed: <name>", with the run link and commit. A workflow that keeps failing adds one comment every 6 hours, not one per run. The issue **closes itself** when the workflow passes again. Not for pull requests or other branches |
| An unexpected error in production, or in a browser | Sentry | the Sentry project; rules below |

Set up once (yours):
1. GitHub, this repository, **Watch** (top right) → **Custom** → tick **Issues** (or "All activity"). Without this GitHub does not e-mail you about issues the workflows open. Check your e-mail address under Settings → Notifications.
2. Sentry, project, **Alerts → Create Alert → Issues**. Three rules are enough: (a) "A new issue is created" → send an e-mail to yourself; (b) "The issue is seen more than 10 times in 1 hour" → e-mail; (c) condition "The event's tags match `source` equals `cron`" → e-mail every time (a failed daily job). Events carry the tags `source` (worker, browser, cron) and `route`. Then press "Send a test event" on `/admin` and check that an e-mail arrives. (Sentry's screens change; the idea is: new issues, spikes, and anything from the cron.)
3. Optional: an uptime service on `/api/v1/health` and `/api/v1/health/jobs` for minute-level alerts (the Watchdog is hourly, and GitHub may start a scheduled run late).

Test it: Actions → **Watchdog** → Run workflow (green means all three checks passed). To see the failure path without breaking anything: `GITHUB_WORKFLOW="Alert self-test" GITHUB_REPOSITORY=<owner>/<repo> GITHUB_EVENT_NAME=workflow_dispatch node .github/scripts/workflow-alert.mjs failure`, then the same with `success` (needs `gh auth login`); it opens and closes one issue. (Done once on 22 Oct against the real repository.)

Limits to know: GitHub pauses scheduled workflows in a repository with no activity for 60 days (push anything or run one by hand to wake it; the alerts cannot tell you that they themselves stopped); a private repository has 2,000 free Actions minutes a month, and an hourly watchdog of about one minute uses roughly 720 of them.

## Literature scan (27 Oct 2026)

Design and numbers: [design/litscan.md](design/litscan.md). A scan is a row in `litscans` with its events in `litscan_events` (migration 0020) and a Cloudflare Workflow (`LitscanRun`, binding `LITSCAN`, named `scholar-litscan` in production and `scholar-litscan-staging`; the first deploy that contains it creates it, nothing else to set up).

- **Look at one:** `npx wrangler workflows instances list scholar-litscan`, `... describe scholar-litscan litscan-<scan id>` (the instance id is `litscan-` and the scan's id). A person's scan list is on the page; for yourself: `SELECT id, state, updated_at FROM litscans ORDER BY created_at DESC LIMIT 10`.
- **A scan stuck on "running":** nothing to do. A running scan that has not moved for 12 minutes is ended as `failed` the next time anyone reads it; the person can start another (one at a time). The engine tries a failed step 3 times; a sub-question that still fails is a gap.
- **Logs:** one line a finished scan (`litscan_done`: how many sub-questions, how many answered, the language, the time) and one line for a search that found nothing or that a source refused (`litscan_search`: which sources failed and with what words, e.g. `OpenAlex HTTP 429`). Many `HTTP 429` lines mean the sources are being asked too fast: the lane is `GATES.litscan` in `src/gate/index.ts`.
- **Counts:** the admin page, "How answers went", feature "Literature scan" (answered, nothing found, no paper about it, no abstracts, the papers do not answer, an answer that could not be checked, too slow, allowance used, unavailable). A rising share of "unavailable" or "too slow" is the thing to look at first.
- **What it keeps and for how long:** the topic, the approved plan and the checked report, 24 hours (the daily clean-up deletes past `expires_at`), the count of scans started today 35 days; all of it goes with an account and is in the data export (`literatureScans`).
- **Limits** (shared constants in `packages/shared/src/litscan.ts`): topic 8 to 400 characters, 2 to 6 sub-questions, 4 scans a day, one at a time, 6,600 tokens a sub-question shown as the estimate and refused when the day's 60,000 cannot cover it, 75 s for the model per sub-question.
- **A new event type in the scan stream:** add it to `LitscanEvent`, classify it in `stream-shape.ts` (`LITSCAN`), and run `scripts/litscan-e2e.mjs`, which checks every stream it reads.
- **Staging check with the real model and sources:** `node apps/api/scripts/staging-session.mjs make 2 <file>`, then `APP=https://scholar-staging.shodhsetu.workers.dev SESSIONS=<file> node apps/api/scripts/litscan-live.mjs`, then `... staging-session.mjs cleanup`. It prints the plan, the time of every event, each section and the tokens by label (`litscan_plan`, `litscan_worker`).

## A literature scan shared by a link, and the refresh of old open-access papers (28 Oct 2026)

- **Shared links** (`litscan_shares`, migration 0021): `GET /api/v1/litscan/shared/<token>` needs no sign-in and returns the scan without its owner. A wrong, turned-off or expired link is one 404. To kill a link by hand: `DELETE FROM litscan_shares WHERE scan_id = '<id>'`. A person can have 5 at a time; the link ends with the scan (24 h), by the daily clean-up, or with the account. The static host adds `noindex`, `no-store` and `Referrer-Policy: no-referrer` for `/literature-scan/shared/*` (`apps/web/public/_headers`).
- **Refresh of a paper in the shared index** (`oa_papers.content_hash`, `refresh_at`, migration 0022): a ready paper read more than 180 days ago is fetched again when someone asks it. Look at one: `SELECT key, status, attempt, ready_at, refresh_at, content_hash FROM oa_papers WHERE key = 'doi:…'`; the instance is `oa-<hash>-<attempt>` as for a first reading (`npx wrangler workflows instances describe scholar-oa-ingest <instance>`). A refresh that cannot fetch leaves the paper `ready` and moves its `ready_at` to 150 days ago (it is tried again in 30 days). To refresh a paper now: `UPDATE oa_papers SET ready_at = datetime('now', '-200 days') WHERE key = '…'` and ask it once.
- **Retractions at ask time:** the `paper` event of `POST /papers/oa/ask` carries `retracted: true` from Crossref's data through the public cache (a day). A failed lookup is silent by design.
- **Running two Workers locally** (an experiment beside a test run): `INTEGRATION_PORT`, `INTEGRATION_STATE` and `INTEGRATION_CONFIG` change the runner's port, state folder and generated config; the fake identity provider of the suites is on 9911, so only one suite or evaluation can run at a time. A model comparison belongs in its own `git worktree` (its own folder, its own `wrangler dev`), so it does not watch the folder you are editing.

## The support judge (28 Oct 2026)

Every answer of the prompt box, and every sub-question of a literature scan, is read a second time: a model (Llama 3.3 70B, then Mistral Small 3.1) says which sentences of the cited abstracts support each claim; unsupported claims are left out ([claim-support.md](design/claim-support.md)). It costs one more call per answer: about 2,500 tokens (2.3k in, 0.2k out), about 0.024 cent and 7 s, counted in the person's 60,000 a day like any other call (so a day holds about nine searches instead of fourteen; a scan sub-question is estimated at 5,500 tokens, it was 3,000).

- **Switch it off**: set the Worker variable `CHAT_JUDGE` to `off` (`wrangler deploy --var CHAT_JUDGE:off`, or in the dashboard). Answers are then shown as before, without a `checked` flag, and the banner says only that each mark points at a sentence. Use it if the model service is failing for long or the AI cost must stop. Nothing else changes. **A deploy by CI replaces what was set by hand** (the next push to `main`, `wrangler deploy` without `keep_vars`): to keep it off across pushes, put `"CHAT_JUDGE": "off"` in the top-level `vars` of `apps/api/wrangler.jsonc`, and for staging in `env.staging.vars` (the reasons are under "Context between messages" below).
- **When the judge fails** (a timeout of 20 s, an error, a reply that does not fit) the answer is shown as written and the banner says the claims were not read against the sentences. One log line a call: `chat_judge` with the counts of verdicts, `leftOut`, `ms`, the model, and `error` when it failed (never a word of the question, the answer or an abstract). Many `error` lines in a row mean the judge's models are down; the usage page shows the label `chat_judge` (and `litscan_worker_judge`) per model.
- **Check strictly** (`POST /api/v1/chat/tighten`, 29 Oct 2026): the reader asks for a slower, stronger reading of an answer ([claim-support.md](design/claim-support.md), section 4). It uses gpt-oss-120b (20 to 45 s, about 5,000 tokens) plus a quick second reading, counts in the person's day like any call, and has its own limiter (the AI bucket, `ASK_LIMITER`). `CHAT_JUDGE=off` switches it off as well (503 "switched off"). Logs: `chat_judge` lines with `rewritten`, `offered`, `checkMs`; usage labels `chat_strict` and `chat_strict_recheck`. About 5% of calls fail (the model's stream is cut); the reader is told and can press the button again. Nothing of the request is stored.
- **Check it**: `node apps/api/scripts/support-eval.mjs --split=all --gate` against a local Worker with a real model (it runs every week in `qa-eval.yml`); the labelled claims are `apps/api/scripts/fixtures/support-gold.json`.

- Mail: **Cloudflare Email Routing** (Free) forwards `team@sodhsetu.in` (the contact address on the legal pages) and `privacy@sodhsetu.in` (the grievance address) to the owner's own inbox; the catch-all is off. - Three pictures are drawn by Rive files: the bridge on a running scan, the box in the upload zone, the scene beside an upload ([design/setu-rive.md](design/setu-rive.md), [design/rive-ideas.md](design/rive-ideas.md)). They are decoration: the page is whole without them and every fact is in text.

Nothing of it is in the first load, and `scripts/budget.mjs` fails the build if any of it is, or if a chunk grows past its line.

It will not fetch from a `data:` address, so `vite.config.ts` never inlines a `.riv`; a build that did would show no picture for the two small files. If a browser cannot start the main wasm the runtime asks a CDN for a fallback, which the CSP refuses.

Edit the generator in `apps/web/rive/<name>/`, build, copy the `.riv` into `apps/web/src/assets/rive/`, and commit both: [the folder's README](../apps/web/rive/README.md). CI does not have the CLI, so it cannot check that the committed file is the generator's.

## Context between messages, and Copy and Edit (2 Nov 2026)

The prompt box in Auto can send the earlier turns of the chat (`history`) and, by the person's choice, a few questions of earlier chats (`earlier`) with a message ([design/chat-actions-context.md](design/chat-actions-context.md), parts B and C). The server keeps no chat: both fields come from the browser, are read by one never-throwing reader, capped (at most 3 turns and 3,000 characters; 3 earlier questions and 800 characters), and are data for working out what a message refers to, never evidence and never an instruction. A body over 80 KB (`MAX_CHAT_BODY_BYTES`: the largest legal message, 20,000 Devanagari letters, is 60,000 bytes) is a 413 `too_large`, by its `Content-Length` and by counting the bytes of a chunked body; a history of the wrong shape is a 400 `invalid_history`; `history` or `earlier` with a mode other than Auto is a 400 `invalid_flag`. Only a signed-in person's message is read by a model with them; for anybody else the fields are checked and ignored, and the browser does not send them for a visitor. Copy and Edit-and-resend are browser features and send nothing of their own.

- **Switch it off: the Worker variable `CHAT_CONTEXT` set to `off`** (`wrangler deploy --var CHAT_CONTEXT:off`, or in the dashboard). With it set, `history` and `earlier` are neither read nor refused (no `invalid_history`, no `invalid_flag`, as an older server would behave): every message is answered as before this change (a follow-up is a new search of the words, a greeting is a greeting), nothing else changes, and a message that came with either field and ends answered or refused is counted `followup_context_ignored` (counts only). Any other value, or no variable, leaves it on. Use it first if answers got worse or the model failed more after the release, as with `CHAT_JUDGE`. Check after setting it: send a follow-up through the page and look at the `understood` step (no "Using your earlier question" line).
- **The browser does not know about the switch.** There is no kill switch on the browser side. With `CHAT_CONTEXT=off` the browser still builds and sends both fields for a signed-in person in Auto, and the server drops them unread (nothing of them is logged or read by a model, but they still reach our Worker, as the privacy text says), the chip "Continuing from: ..." and the Settings switch "Use my earlier chats" still look active, and the line "Used from your earlier chat" never appears. To stop the browser sending them, a new build is needed.
- **A deploy by CI replaces what was set by hand.** Variables set in the dashboard or with `--var` last only until the next `wrangler deploy`, that is the next push to `main`. Checked, not tested live: `.github/workflows/ci.yml` deploys with `npm run deploy -w apps/api`, which is plain `wrangler deploy`; `apps/api/wrangler.jsonc` has no `keep_vars` (and no `--keep-vars` is passed), and in the installed wrangler (4.152.0) `keep_vars` (or `--keep-vars`) is what makes a deploy keep the plain-text variables it does not have in its own config (read in its source, `keepVars` adds the `plain_text` and `json` bindings to the ones kept). To keep it off across pushes, add `"CHAT_CONTEXT": "off"` to the top-level `vars` of `apps/api/wrangler.jsonc` and push. `vars` is not inherited by an environment (wrangler marks it not inheritable, and the staging block repeats its own `EXPECT_CRON`): a lasting switch for staging also goes in `env.staging.vars`, and staging is deployed by hand (`npm run deploy:staging -w apps/api`). The same holds for `CHAT_JUDGE`.
- **Switching it off does not change the privacy text.** The text says earlier messages are sent when a follow-up needs them; with the switch off it says a little more than happens, which is safe. Removing the feature for good changes what the text promises, so the text and `PRIVACY_VERSION` change again.
- **What it costs, and where to look.** A follow-up that a model reads with the earlier turns costs about 1,200 to 1,700 tokens more (a chars/4 estimate in English; Hindi and Hinglish not measured; **not yet measured on the real model**: `node scripts/router-eval.mjs --followup [--set=tuned|holdout|all] [--gate]` was written and is wired, needs a local Worker with `ENABLE_DEV_ROUTES=1` and the real model, and has not been run), counted in the person's 60,000 a day like any call. The router call that read the turns carries the usage label `chat_route_ctx` (the usage page shows it per model, so the real extra cost shows). The 203-message router eval is untouched and must stay at its result.
- **The pre-flight bar.** Before a model reads the turns, the server checks that the person's day still has `FOLLOW_UP_TOKENS_ESTIMATE` (11,000 tokens: router with turns 1,200 to 1,700, writer about 5,000, judge 3,900) left, from the usage log (`tokensToday`; the quota is checked before each call and is not atomic). If it has not, the words are searched as written (as for a visitor, and the search is free), the papers are shown with no written answer and the reply ends `done` with reason `quota`, counted under `quota`. A first message is not held to this bar.
- **The outcome names** ("How answers went" on `/admin`). For a signed-in person's message that came with earlier turns, `answered` and `not_grounded` are counted as `followup_answered` and `followup_not_grounded`, even when the rules settled it without a model; `followup_rewrite_failed` is such a message whose restatement the server did not use, or whose model call failed or timed out (the words were searched as written; either ending), and `followup_context_ignored` one that carried `history` or `earlier` while `CHAT_CONTEXT=off` (either ending). Every other ending keeps its name (`not_answered`, `quota`, `routed`, `small_talk`, ...). The headline sentence of that table counts the follow-ups in (`chatRefusalShare`: `followup_answered` and `followup_not_grounded` count like their first-message twins); the two names that hide how they ended are not guessed into it and are counted apart ("N follow-ups are left out of this share"). Compare the "unavailable" share before and after the release, as for the 3,000-character abstract limit.
- **What the person sees** (the names to look for in a screenshot): "Using your earlier question: ..." with the button "Use these exact words" (not offered for a message about the same papers); "Papers from 2022 or later" as a chip, with a button that removes the year filter and searches again; "Used from your earlier chat: ..." with "Do not use it and search again"; "Continuing from: <title>" and "Private chat: not kept, not used as memory" above the box; a line under a year filter that leaves few papers ("Only 3 of the papers found are from 2020 or later ...") or none, under its own notice kind `years` (it has no "Search again": asking again gives the same list).
- **Never logged.** Workers observability is on, so a `console.log` of a message would be kept by Cloudflare. No log line carries history or `earlier` text (a test fails if one does). The follow-up lines are `chat_followup` (counts and short names: turns, earlier, mode, intent, rewrote, fellBack, check, whether a year range) and the warning `chat_history_refused` (no content); a failure of a message that came with turns is logged by kind only (timeout, malformed, quota, unavailable, error), never the provider's own error text. The AI usage log (`llm_usage`, 90 days) holds, tied to the account id: the task, the model, token counts, the label (`chat_route_ctx` for the router call that read the turns), the time and whether it worked, never a word of what was written. `chat_debug` and `chat_general_debug` lines are dev-only and a follow-up never writes them.
- **On the device.** Chats and their index are in the browser's IndexedDB `chats` store and the `scholar.chats.v1` list. An entry carries `owner` (the account id of the person who made the chat), `kw` (a few words of the person's own questions and of the English words their searches used, so that "Use my earlier chats" can find the chat; never from an answer) and `nomem` ("Do not use this chat as memory"); they go with the entry when the chat is deleted, at the 30-chat limit, on "Delete all" and on sign-out. A reply that used questions of other chats keeps up to three of them in its own record until its own chat is deleted, even if the source chat is deleted first (the privacy text says so). Whose chats: a different person signing in on the browser removes the chats of the one before (from the list and from IndexedDB); a sign-in that only runs out (the cookie lasts 30 days and is not renewed) does **not** remove anything: the owned chats are held, out of sight and not used, in storage until the same person is back, and are the first to go when the 30-chat list needs room; sign-out sets `scholar.wipe` first, so a tab closed part way is finished by the next page. Each record has a revision, so a tab that was left behind cannot write its old copy over another tab's. The Settings switch "Use my earlier chats" is `scholar.earlier`, which holds the **account id of the person who turned it on** (anyone else, and a visitor, reads it as off; it stays through a sign-out like the Indian sources switch; off when storage is blocked). Do not rename a `scholar.*` key or the IndexedDB name: it deletes people's chats (see "The product's name").

## The Trending list (3 and 4 Nov 2026)

The "Trending" row of the Home page is a list of research phrases that have more journal papers than a year ago (built; the release is committed with the job off, see LAUNCH DARK). Plan and decisions: [design/chatview-and-trending.md](design/chatview-and-trending.md) (T1 to T12; sections 8 to 13 say what was built, what differs from the plan and what was not built). The list is made by a job from open data, never written by a person and never by a model of ours: a phrase is the exact name of an OpenAlex keyword, unchanged. **The words are model-assigned upstream:** OpenAlex's own indexing assigns its keywords to papers with a small model that reads each paper's title, abstract and venue (https://help.openalex.org/data/keywords/, read 4 Nov 2026; the page says an AI judge rated 91% of the keywords accurate), so the owner's rule "never written by a model and never taken from a title or an abstract" is met by our service and cannot be met by any OpenAlex source (its topics are model-assigned too). The Why panel says so, and the privacy page will when the job goes live (its bullet is written and held back from the first deploy: LAUNCH DARK, step 4); whether to accept that, or to look for another source, is the owner's (design note, T7). The file (`TrendingPayload`, `packages/shared/src/trending-client.ts`): `{ version: 1, asOf: "2026-11-03", generatedAt, validUntil (generated plus 48 hours), poolAsOf (the day the weekly pool was computed), disabled, groups: { global: { chips }, in: { chips } } }`, and a chip is `{ text, sinceYear, a, b, field }`: the keyword's own text, the year its search starts from (the year before the day's), its journal papers in the 91 days that end 45 days before the day (`a`) and in the same dates a year earlier (`b`), and its OpenAlex field. At most 12, one a field, four a domain, for each group; `global` has 8 to 12 (the job writes nothing under 8), `in` any number. The stand-ins' file (nine phrases for everyone, three for India) is 1,357 bytes, about 110 bytes a chip, so the file is under 3 KB at its largest (24 chips).

What the route answers: the file, when the page's own reader accepts it and it is fresh (before `validUntil`, and a pool dated no more than 13 days ago: a pool dated 14 days ago is already out, because the 14 days count from that day's midnight); `disabled: true` with no chips for the flag or the variable (`off` or `dark`); for a store that throws a 503 (`no-store`) with the same empty file; and for anything else (a miss, no KV, a file that is not right, a stale file) a valid, empty file that has already expired. A stale file is never passed on: the server checks what the page is to check. Tested against a real local Worker (`scripts/trending-e2e.mjs`).

**What the job does**

- **Every day, first**, from the pool: a phrase from computing, mathematics or physics must also be growing on arXiv (submissions in the last 30 days against the same 30 days a year ago, at least 1.3 times and at least 40; the 30 days before are asked too and gate nothing); a phrase from any other field needs a score of 1.5 (there is no second source for it). Every phrase is then searched with the product's own search (the same five sources and merge as the chat, the Indian sources for the India list, 40 results as for a search with a year filter) and must pass the verifier: at least 20 results, 10 with abstracts, 5 of the first 20 from the year before the day's year on (so between 12 and 24 months, not the plan's "24 months"), none retracted among the first 20, no journal with more than half. The list is picked with hysteresis (a phrase shown yesterday stays unless another scores 1.25 times higher), at most 12, one a field, four a domain (the plan's two a domain cannot give 8 phrases with Health held, which leaves three domains). It is written only if 8 phrases are left. A phrase is **not shown that night** (and the next night asks again) when arXiv could not give its counts after its one retry (`rejected.unconfirmed`; **three phrases in a row** that arXiv cannot answer is an outage and fails the run), when the search's own retraction check (Crossref) did not answer (`rejected.unchecked`: with no answer "none retracted" would rest on OpenAlex's flag alone, which is nearly blind for fresh papers), or when it is in the owner's deny list (`denied`: the list holds the day's file too, not only the weekly pool; whole phrases, as the pool writes them, so a longer phrase that contains a denied one needs its own entry). **On any other error (OpenAlex, KV, the pool, the call budget, a search that no source answered, three arXiv failures in a row, a deny list that is there and cannot be used) nothing is written and the last good file stays** (it is served until its `validUntil`, 48 hours after it was made).
- **Weekly (Monday, or when the pool is missing or 7 days old)**: the scan. For each of the 243 subfields that are not `never` (`packages/shared/src/subfield-policy.ts`: 252 in all, 153 allowed, 90 held, 9 never), the keywords of the last quarter and of the same quarter a year earlier, for everyone, and for the 153 allowed subfields also for papers with an author at an Indian institution. Then the best candidates are asked their journals and countries, and the most substantial ones that last year's top 200 did not have their exact count. What passes is the pool: about 40 phrases (20 for India). A new pool under 10 phrases is refused and the old pool kept. Health subfields are scanned for everyone and their phrases are only logged (`scan.held` in the log line); they are never shown. A scan that is part way goes on the next days (up to 6 days after it started: the day's file comes first, so a slow night may leave the scan only a few batches; the old pool is good for 13 days and a scan begins when it is 7 days old). **A pool that is 10 days old when a run ends** (no new scan has finished) makes that run fail, with the days in its message, so the heartbeat and `/health/jobs` say so while the list is still being shown and four days before it goes; a run with no time for a batch is otherwise not an error. **A Monday whose pool was refused as too small (and, in principle, one with no time to begin) is tried again the next Monday, not the next day**: only a scan that has started is made up the next day.
- **The scan is done in batches** of 10 subfields whose counts wait in KV (25 batches; an estimate from the size of a keyword row, not measured on a real scan: about 4 MB in all, 200 KB the largest, against KV's 25 MiB for a value), so that a run that has no time left goes on in the next one. A second run that starts while one is scanning does not scan (a lease in `trending:v1:scan`, 11 minutes).
- **When the heartbeat says failed.** A run reports the first error it met, after it has done what it could: a day's file that was made and published still stands when the scan after it failed, and the heartbeat then says failed for the scan's error (`/api/v1/health/jobs` 503) although the page has a good list.

**The platform's limits, and why the job is shaped as it is** (Cloudflare's Workers limits page and KV limits page, read on 3 Nov and again on 4 Nov 2026; Workers Paid is what `docs/roadmap.md` and the backup section of this runbook say the account is on, not checked in the dashboard): a Paid invocation may make **10,000 subrequests**, and KV, D1 and R2 operations count (the Free plan allows 50: the job cannot run there); **6 connections** at once; a scheduled run may last **15 minutes** (CPU 15 minutes for a schedule that runs less often than hourly); **1,000 KV operations** an invocation (the two pages disagree: the Workers page says 10,000 subrequests an invocation, KV included, and the KV page 1,000 operations for Free and for Paid alike; nothing here deploys to find out, so the smaller figure is the rule); a KV key may be written **once a second** (the job waits before a second write of a key). The two other jobs share the invocation. **The verifier's searches keep their cache in memory** (`jobSearchEnv`, one cache for the whole run): with the visitors' cache a cold search made 92 KV operations of its own (a read or a write for every provider list, every DOI check and every retraction entry; measured on 4 Nov with the real search code on stand-in providers), which the job's own count of 900 does not see. In memory a cold search is about 8 requests and 9 calls to the shared lanes (Crossref, DOAJ, Semantic Scholar), and none to KV. **Before the flag is taken out, read one real night's log line (`calls`, `kvOps`, `ms`) and Cloudflare's own count of that invocation's subrequests**: no real run has been made. Measured with live calls on 3 Nov: an OpenAlex keyword question takes 1.1 to 4.4 seconds and costs $0.0001; the answer carries the subfield's total (`meta.count`), so there is no call for that. That a bulk get is one KV operation toward the invocation's limit is the KV limits page's word ("A bulk request to Workers KV counts for 1 request to an external service", read 4 Nov 2026); what it costs is another matter: the pricing page bills a bulk read by the keys it reads.

**Turn it off**

1. **The flag, at once (the server in about two minutes; a browser up to seven; a returning visitor one more Home screen):** `npx wrangler kv key put trending:v1:off 1 --binding CACHE --remote` (run in `apps/api`; the flags are those of wrangler 4's own help, read on 4 Nov). The route then answers `disabled: true` with no chips and the page is to show no Trending row. The job keeps running and keeps making the list (so you can still read it). It survives deploys. **Real bounds, not "a minute":** KV takes up to about a minute to reach every place, the place that serves the route keeps what it read for 60 seconds (`cacheTtl`), and the answer may be kept 5 minutes by a browser or an edge (`max-age=300`): about 2 to 7 minutes. Then the page: the Home screen that is already open never drops its row (nothing moves under a reader), and a returning visitor whose device copy of the list is under 24 hours old is shown it once more on the next Home screen; the `disabled` answer then clears the copy (`DEVICE_COPY_MAX_AGE_MS`, `decideFetched`). **A device whose request fails, is not answered within 2.5 s, or gets an answer that is not a list keeps its copy and shows the row each time Home is drawn until the copy is 24 hours old**, so "the flag reaches everyone in minutes" is true of the server and not of every screen. For a phrase that must not be seen at all, use the deny list (step 4) as well as the flag: it makes the next file clean, but a copy already on a device still holds the old phrases for up to 24 hours. If that is too slow, shortening the copy's age is a one-line change of the page (the price is a row that is not there at the first paint).
2. **Back on:** `npx wrangler kv key delete trending:v1:off --binding CACHE --remote`.
3. **The variable** (`off` stops the job too, and the route answers disabled without reading KV; `dark` lets the job go on and the route hide the list; `wrangler.jsonc` has `off` until a first list has been made by hand and read): `wrangler deploy` with `--var TRENDING:off`, or in the dashboard. **A deploy by CI replaces what was set by hand**: to keep it across pushes put `"TRENDING": "off"` in the top-level `vars` of `apps/api/wrangler.jsonc` (`vars` is not inherited by staging, which has no schedule and an empty list).
4. **To throw the list away** (a wrong phrase got in): put the phrase in the deny list, `npx wrangler kv key put trending:v1:deny '["phrase one", "phrase two"]' --binding CACHE --remote` (in PowerShell put the JSON in a file and use `--path deny.json` instead); it is applied **to the next run's file** (the nightly 03:17 UTC run) and to the next weekly pool, so a phrase is out by the next morning; until then the flag hides the list. Whole phrases only (case, hyphens and spaces do not matter, but a longer phrase that contains a denied one is a different phrase: add it too). **A deny list that is there and cannot be used** (not JSON, which is what PowerShell makes of an inline list; not a list of text; over 1,000 phrases; KV unreadable) **fails the run with a message that says so, and the last file stays**: it never silently denies nothing. An empty value or `[]` is no list. Do not write a list into `trending:v1` by hand: the page would show it as trending.

**Read the list**

npx wrangler kv key get trending:v1 --binding CACHE --remote --text        # the file the page is to read
npx wrangler kv key get trending:v1:pool --binding CACHE --remote --text   # the pool: scores, counts, and "held" (health phrases found and not shown)
npx wrangler kv key get trending:v1:scan --binding CACHE --remote --text   # progress of the scan: next batch of batches
curl -s https://sodhsetu.in/api/v1/home/trending                           # what a visitor's browser gets (while TRENDING is dark: disabled, no chips)
curl -s https://sodhsetu.in/api/v1/health/jobs                             # three jobs, each ok

The log line of a run (Cloudflare, Workers, Logs; `{"msg":"trending","result":...}`) says what it did: the phrases it published (public words from OpenAlex's own list, no person), how many it refused and why, the scan's progress, calls and KV operations used, and the held phrases. When the job fails the heartbeat says so (`/admin`, "Scheduled jobs", `/api/v1/health/jobs` 503) and Sentry gets it with the tag `source: cron`. What the errors mean: `only N phrases can be shown` (verification took too many out: look at the pool and the sources), `the new pool is too small` (the scan gave under 10 candidates: OpenAlex answered oddly; the old pool is kept), `openalex: http HTTP 429` (the day's $1 is used up: see "OpenAlex budget"), `arxiv: error_entry` (arXiv answered its Error feed; the next day tries again), `search: no source answered` (every source of the product's search failed for a phrase), `call budget used up` (a limit above was reached: a bug or a bigger taxonomy), `the daily file ran out of time`, `the deny list ... cannot be used` (fix `trending:v1:deny` or delete it: nothing is written until then), `the weekly pool is N days old` (the weekly scan is not finishing: read `trending:v1:scan`; the list goes when the pool is 14 days old).

**Start it sooner than the nightly cron (there is no "Run" button to press)**

Once `TRENDING` is `dark` (LAUNCH DARK, step 4), the first list is made by the cron like every later one, at 03:17 UTC (08:47 in India). With no pool yet the first night scans and makes the pool, and the first file is made that night or the next. Read the run under Trigger Events (Settings, Triggers, "View events") and in the log line. With no pool the first run scans (5 to 9 minutes, arithmetic) and the next run goes on from where it stopped (the day's file is made first, whenever there is a pool). A second run that starts while one is on the scan skips the scan as "busy". The scan's lease is let go whenever a run ends, however it ends (done, an error, or the job's own 9- and 11-minute stops: `finally` in `job.ts`), so a second trigger straight after a run that ended is not held up; only a run that the platform kills before it can release it (out of memory, the 15 minutes) leaves the lease standing, for up to 11 minutes (`leaseMs`), and the trigger inside those minutes skips the scan.

To hide it again at once without a push, `npx wrangler kv key put trending:v1:off 1 --binding CACHE --remote`.

Nothing is left to a step that can be forgotten before the push. The reverse is the owner's to remember: after the push of step 5 the list is public. The KV flag `trending:v1:off` is a separate, faster switch and stays as it is.

**Privacy text.** The job sends nothing about a person, and nothing a person wrote: it has no sign-in, no database row of a person and no model (`legal-text.test.ts` reads the job's source for this). The only words it sends out are OpenAlex's own keywords, which OpenAlex itself assigned to papers with a model of its own: the bullet says so (an earlier draft said that no AI service reads or writes any of it, which was not true of the words themselves). It sends OpenAlex and arXiv public count questions, and it sends each phrase it may show to the sources of the product's search: OpenAlex, Semantic Scholar, Crossref, PubMed and DOAJ, and for the India list OpenAlex and DOAJ only (Shodhganga is read through OpenAlex; its own site is never fetched), plus the DOI and retraction checks that every search makes (Crossref, doi.org). The sources see the Worker's address and the contact address in `CROSSREF_MAILTO` (in arXiv's User-Agent and as OpenAlex's `mailto`), never a visitor. **The privacy page's bullet is written and pinned, and held back from the first deploy** (branch `trending-privacy-text`: it describes a job that runs only from LAUNCH DARK, step 4, and the owner and a lawyer read its wording first): one bullet of "Your papers and ideas" ("In the background, once a day ..."), pinned by `apps/api/src/legal-text.test.ts` against the code. `PRIVACY_VERSION` was not changed (`2026-11-draft-14`): the bullet describes a job that touches no person and changes no promise made to one; whether to bump it, and the wording, are the owner's and a lawyer's. The Settings page needed no sentence: it says nothing about the sources. The Home row is built: the page's own request for the list (to our address only, no cookie, after the first paint) and the copy of the public list it keeps on the device for at most 24 hours (`scholar.trending`: the file's own fields and the time it was kept, nothing about the person) are public data. The privacy page says that copy too, in the same bullet (your browser keeps a copy of the public list and uses it for no more than a day, an older copy is removed the next time Home is opened, and it holds nothing about you: a copy that may not be used any more stays in the browser until Home is drawn again, which is why the page does not say "keeps for up to a day"), and `legal-text.test.ts` pins it against `DEVICE_COPY_MAX_AGE_MS`, the one `localStorage.setItem` of `lib/trending.ts` and the line that removes an old copy; its wording, like the rest of the bullet, is the owner's and a lawyer's.

## MCP server: AI apps use Sodhsetu (6 Nov 2026, built, OFF)

What it is: `https://sodhsetu.in/mcp`, a remote MCP server (Streamable HTTP) on the same Worker, so that Claude, ChatGPT, Cursor or VS Code can search papers (`search_papers`), check a reference list (`verify_references`), look up retractions (`check_retractions`), ask one paper a question (`ask_paper`), read and add to the person's library (`get_library`, `save_paper`) and, behind a switch of its own, check a claim against up to five papers (`check_claim`), for a signed-in person. Docs "Sodhsetu understanding, follow-ups and MCP (design)", pages 10-15 (M6, M7, M8). Code: `apps/api/src/mcp/`; the tools call the same services as the website (`src/search/service.ts`, `src/references/service.ts`, `src/search/retraction-service.ts`, `src/oa/service.ts`, `src/library/service.ts`, the strict support judge in `src/chat/claim-check.ts`), never `/api` over HTTP.

- **Phase 2 and 3 tools** (M8):
  - `ask_paper` is "Ask this paper": the same daily allowance and the same 20 new papers a day per person. It waits 45 s for a paper being read, then answers `still_reading` (the reading goes on).
  - `get_library` pages the person's own library.
  - `save_paper` saves by DOI. Sodhsetu looks the paper up itself, and nothing about it comes from the app. It saves only with the person's yes:
    - `confirm: true` from the app, which its description says to set only after asking;
    - or Sodhsetu's own question to an app that can ask the person (MCP elicitation, protocol 2026-07-28).
  - `check_claim` is the strict reading of "Check strictly" (the `qa` chain, gpt-oss-120b) on one claim against the abstracts of up to five DOIs; retracted papers are never evidence. It is listed only when its switch lets the account in.

- **Packages**: `@modelcontextprotocol/server` 2.3.1 (its own stateless `createMcpHandler`: a fresh server per request, the 2026-07-28 protocol and the 2025 one; no Durable Object and no Agents SDK, whose `McpAgent` Cloudflare's docs now mark deprecated), `@cloudflare/workers-oauth-provider` 1.2.4 (OAuth 2.1 with PKCE, dynamic client registration, the discovery documents, the token endpoint and the check of each bearer token), `zod` 4.6.7 (the tools' schemas). The OAuth library is loaded only on the MCP paths. The Worker grew from 827 to 1,025 KiB gzipped.
- **Sign-in**: the app sends the person to `/oauth/authorize`; a person who is not signed in uses the website's own Google or ORCID sign-in (no new address to register with Google or ORCID) and comes back to a consent page (written by the Worker, no script, never framed) naming the app, where it sends the person back, and what it may do. Scopes: `papers:read`, `references:verify` (what an app that names no scope gets), `library:read`, `library:write` (granted only to an app that asks for them, by name or by the step-up challenge of `get_library` / `save_paper`; the consent page then names them). Tokens last an hour; a grant ends after 30 days without use (90 days at most). Settings, **Connected apps**, lists the apps and disconnects one at once; erasing an account disconnects them all.
- **Limits**: 300 tool calls per account per day (`mcp_daily`) and the website's per-minute limiters keyed by the account (`search_papers` 60, references 120, counted per reference). Answers stay under about 8,000 tokens (`next_cursor` for more). Counts only (`mcp_calls`: tool, app name, time, outcome; 35 days): never a query, a reference or a DOI. Admin page: "AI apps (MCP server)".
- **Switch** `MCP` (Worker variable): unset = **off** (every MCP path answers the 404 it did before; Connected apps is hidden), `beta` (only the account ids in `MCP_BETA_USERS`, commas between them; anyone else sees "closed beta"), `on`. `npx wrangler kv key put flag:MCP off --binding CACHE --remote` lowers it within a minute without a deploy (it can never raise it). Without the `OAUTH_KV` binding the server is off whatever `MCP` says.
- **Switch** `MCP_CHECK_CLAIM` (Worker variable, the same reader): unset = **off** (`check_claim` is not listed), `beta` (the accounts of `MCP_BETA_USERS`), `on` (every account the server lets in). `flag:MCP_CHECK_CLAIM` in CACHE can only lower it. Its eval (`eval/claim.eval.ts`, recorded live and replayed in CI) is the gate: no claim a person labelled unsupported may be called supported.

**To run the beta** (the owner's steps, in order):
1. `npx wrangler kv namespace create OAUTH_KV` (and the same with `--env staging` for staging), and add `{ "binding": "OAUTH_KV", "id": "<id>" }` to `kv_namespaces` in `apps/api/wrangler.jsonc` (the comment there says where). A namespace of its own: `CACHE` holds only public data.
2. Read the privacy sentence (`FLAG_SENTENCES` in `apps/api/src/legal-match.test.ts`, flag `MCP`) and put it on the privacy page under "What we send where" with the next `PRIVACY_VERSION`. The test fails with `MCP` at `beta` or `on` and the sentence missing.
3. Your account id: `/api/v1/auth/me` (`user.id`) while signed in. Set `"MCP": "beta"` and `"MCP_BETA_USERS": "<id>"` in `vars`, and push.
4. In Claude Desktop or claude.ai (Settings, Connectors, Add custom connector) add `https://sodhsetu.in/mcp`; it opens the consent page; Allow. Ask it to check a reference list. ChatGPT (developer mode, connectors) and Cursor (`mcp.json`: `{ "url": "https://sodhsetu.in/mcp" }`) the same way. Watch the admin page's panel and Sentry.
5. `on` when the beta has run clean; the privacy sentence already covers it.

Local: `npm run integration -w apps/api` starts the Worker with `MCP=on` and a local `OAUTH_KV`, and runs `scripts/mcp-e2e.mjs` (the whole OAuth exchange with PKCE, and the tools over the real protocol) and `e2e/mcp.mjs` (the consent page and Connected apps in a browser, with axe); `INTEGRATION_MCP=off` runs the first with the switch off (every path 404). `npm run eval -w apps/api` includes `eval/mcp.eval.ts` (70 fabricated references through MCP, 0 verified; 70 real ones, 70 verified as the right record) and `eval/claim.eval.ts` (check_claim on the support judge's hand-labelled claims; to record again after a change to the strict prompt: `CLAIM_EVAL=record npx vitest run -c vitest.eval.config.ts eval/claim.eval.ts --silent=false` from `apps/api`, with `npx wrangler whoami` showing the account). MCP Inspector, headless: `npx @modelcontextprotocol/inspector --cli http://localhost:8788/mcp --transport http --header "Authorization: Bearer <token>" --method tools/list`.

## Staging

A separate, empty copy of the service at https://scholar-staging.shodhsetu.workers.dev (Worker `scholar-staging`, database `scholar-db-staging`, bucket `scholar-files-staging`, queue `scholar-jobs-staging`),
for trying a change before production. Nothing in it is real people's data. Deploy to it with `npm run build && npm run deploy:staging -w apps/api` (this applies the migrations to the staging database first).
It has no daily clean-up job. Secrets are its own: `npx wrangler secret put NAME --env staging` (today only `SENTRY_DSN`, reported as environment "staging", and `CROSSREF_MAILTO`). To sign in there, add
`https://scholar-staging.shodhsetu.workers.dev/api/v1/auth/google/callback` to the Google OAuth client's authorised redirect URIs, and put the same Google client id/secret in with `wrangler secret put ... --env staging`.
Cost: an empty staging copy is inside the paid plan's included amounts (D1, R2, Queues and Workers requests all have a free allowance that production does not use up); expect cents at most, and nothing while nobody uses it.

## Test everything locally

```sh
npm run build && npm run integration -w apps/api              # auth + library against a real local Worker
npm run integration -w apps/api -- --browser                  # plus the Playwright/axe suites (E2E_BROWSER=chrome|msedge)

INTEGRATION_TRENDING=off npm run integration -w apps/api -- --only="trending"   # the same suite against a Worker started with the variable TRENDING=off (checks that other kill switch)
INTEGRATION_TRENDING=dark npm run integration -w apps/api -- --only="trending"  # ... with TRENDING=dark, the step after the launch state: the job makes the list, the route hides it (the test copy of wrangler.jsonc has no TRENDING line, so the other runs see the list)
npm run test:scripts                                          # the tests of the alert and watchdog scripts (.github/scripts) and the rehearsal helpers
```

The Trending suite changes the Worker's KV through a second dev-only route, `POST /api/v1/dev/kv` (`ENABLE_DEV_ROUTES=1`; it reads, writes, deletes and lists only keys that start with `trending:v1`), and makes the job's stand-ins fail through the key `trending:v1:stub-fault` (`openalex`, `arxiv` or `search`; read only when `QA_STUB=1` and `ENABLE_DEV_ROUTES=1` are both set: `src/trending/stub.ts`). Neither exists in production.

Rule for tests that need to change the database (age a row, rename a table, bring back a deleted account): do it **through the Worker** (`POST /api/v1/dev/sql`, which exists only with `ENABLE_DEV_ROUTES=1`),
never with `wrangler d1 execute --local` from a second process while `wrangler dev` is running. On 22 Oct that made the dev server spin at 100% CPU (over 1,000 CPU-seconds) and stop answering anything, which showed up as
random timeouts in whichever suite ran next. The integration runner's own clean-up between suites works this way too. Also stop a leftover `wrangler dev` (for example from a spike) before running the suites.

## Offline reading (service worker)

`apps/web/public/sw.js` is served at `/sw.js` (`Cache-Control: no-cache` in `_headers`, so a new version replaces the old at the next visit). It does nothing unless a person switched on "Offline reading" in Settings (the page registers it and sends it "on"; the flag lives in the cache `scholar-meta`). Caches: `scholar-shell-v1` (the page, `/assets`, `/pdfjs`), `scholar-data-v1` (the few small reads: paper details, notes, drawing, list, who is signed in), `scholar-papers-v1` (PDFs, the ten last). Reads go to the network first, with a 6 second wait before a kept copy is used. Drawings that could not be sent are in IndexedDB (`scholar` / `pendingInk`).

- **Change what is cached**: edit `readable()` or `isAsset()` in `sw.js`; if the shape of what is kept changes, bump `VERSION` (old caches are deleted when the new worker activates).
- **Kill switch** (if a worker ever misbehaves for everyone): deploy a `sw.js` that contains only `self.addEventListener("install", () => self.skipWaiting()); self.addEventListener("activate", async () => { for (const k of await caches.keys()) await caches.delete(k); await self.registration.unregister(); });`. Browsers pick it up at the next visit.
- Signing out, deleting the account, deleting a paper and switching the setting off clear what was kept (`lib/offline.ts`); a person who signs out with an unsent drawing is asked first.
- Tested by `apps/web/e2e/offline.mjs` with real network cuts (`context.setOffline`).
